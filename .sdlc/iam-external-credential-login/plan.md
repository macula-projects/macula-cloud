## Deviations

- 标识规范化和本地 email grant 协议值从 IAM 私有类提升到 `macula-cloud-system-api` 共享契约，避免 IAM 与 System 写入链出现两套规则；调用方向不变，不扩大远程 API。
- 验证码公开端点新增 `ProtocolLoginCodeDispatcher` 和受控异步执行器；无论账号是否存在都先完成相同的 HTTP 校验并返回统一 `202`，账号查询、Client 路由、供应商耗时与错误均不进入公开响应。证明范围增加 dispatcher 的存在/不存在账号分支和供应商异常吞吐测试。
- external code 防重放增加 `ExternalCodeInfrastructureException` 与 owner nonce claim 句柄，用于只在明确网络或第三方 5xx 故障时安全释放占用；普通认证失败继续消费凭证。证明范围增加 compare-and-release 与 Provider 基础设施失败测试。
- 补充核对企业微信终端 SDK 和钉钉授权登录 SDK 官方文档后，恢复 `WECOM_APP_CODE`、`DINGTALK_APP_CODE`：企业微信原生 code 使用 `cgi-bin/user/getuserinfo` 取得文档字段 `UserId` 并规范为成员 userid；钉钉原生 authCode 复用用户 access token、当前用户及组织成员映射链，最终只接受所配置组织内的 `userId`。APP、browser、webview 仍保留独立 allowlist 与审计语义。
- 飞书、钉钉端内网页统一由业务前端通过 JSSDK 取得 code 后调用 `external_code`，IAM 不再提供 `/login/feishu/webview`、`/login/dingtalk/webview` 或 `webviewBridgeUri` 桥接配置；两种 `*_WEBVIEW_CODE` 继续保留，且只表示第三方 code 的来源与固定核验合同。企微、微信公众号的 URL OAuth 端内入口不受影响。

## Risks

- 当前工作区包含用户未提交的 V8 和飞书/钉钉/微信网页登录代码，且本计划会接触其中若干同名 Client/配置类。任何基于旧版本覆写都会丢代码；实现必须以工作区内容为基线逐块合并，并在每一批次后检查 diff。
- `external_code` 是公共 Client 的一步登录例外，不具备 IAM PKCE 的预绑定证明。固定第三方 App 配置、短期凭证、allowlist、防重放和限流只能降低风险，不能消除凭证在到达 IAM 前被窃取后抢兑的剩余风险。
- Spring Authorization Server 的错误处理默认只输出标准 OAuth 字段；为 `binding_required` 增加 ticket 时若替换整个 failure handler，容易改变 `invalid_client` 的状态码、认证头或缓存头。实现必须只特判受控异常并委托官方默认处理其他错误。
- 共享 token 签发器若错误地改变 refresh token、OIDC、授权记录或 `findByToken(token, null)`，会破坏现有 password/sms/authorization_code。真实 grant type、scope、principal 属性、token 格式/TTL和授权持久化均需兼容性测试。
- MySQL 对排序规则、空字符串和 `NULL` 的唯一性处理会影响 email/mobile。V9 必须按实际列 collation 验证规范化语义；历史冲突会阻塞部署，干净库成功不能代替 V8→V9 升级证据。
- 第三方 code/token 多为 bearer credential。HTTP 自动 3xx、异常消息、响应体、URI 查询串或 debug 日志均可能泄密；所有 verifier 必须固定 HTTPS 端点、禁用重定向、设置超时并使用白名单日志。
- 同一 provider 的 APP、WebView、browser、小程序 code 可能使用不同接口或应用凭据。不能按失败结果轮询端点；每个枚举必须唯一映射 verifier 流程和配置能力，即使底层方法复用也要保留独立审计语义。
- `unionid`、`employee_no`、钉钉 `userId`、企微 `userid` 缺失或生命周期变化会造成拒绝或旧绑定失效。首期按规格失败关闭，不退回 `openid`、昵称、邮箱或手机号猜测绑定。
- Redis ticket、验证码和防重放状态涉及并发与失败恢复。Lua/事务边界错误可能双花、永久锁死凭证或在数据库回滚后消费 ticket；必须覆盖并发、超时、基础设施失败和事务回滚。
- 公共验证码申请端点可能被用于短信/邮件轰炸和 CAPTCHA 消耗。Origin 不是客户端身份证明，必须与 Client/grant 校验、一次性 CAPTCHA、IP/Client/目标摘要限流、统一响应和供应商错误隐藏组合使用。
- Client 到 provider registration 的映射属于认证边界；若缓存失效、配置禁用或 System 校验不一致，可能跨应用换码。System 保存、IAM 加载和运行时 verifier 三层都必须核对 code type、provider 类型、能力和启用状态，映射变更后提交再清理 Client 缓存。
- 非 `EMPLOYEE` 用户类型没有统一标识解析器。未显式实现的 userType 必须拒绝；不能为了通过测试回退全局 `sys_user` 或跨租户查询。
- 真实平台应用审核、权限、设备环境和阿里云服务端合同无法由 Mock 证明。每种 code type 在获得独立测试应用和真实设备验收前都不能标记上线可用。
