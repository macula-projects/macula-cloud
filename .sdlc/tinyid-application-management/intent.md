# Intent: TinyID 接入应用管理
Author: Rain. Status: accepted.

## Problem
平台超级管理员目前无法通过统一管理端查看和管理接入 TinyID 的应用，也无法便捷地维护独立的业务发号配置及访问 Token，只能依赖人工操作数据库。这个过程容易产生配置错误、Token 泄露、权限失控和缺少审计记录等风险，也增加了日常接入、变更和故障处理的成本。

## Proposed outcome
平台超级管理员能够在统一管理端查询、新增和管理 TinyID 接入应用及业务发号配置，并能生成和复制访问 Token、维护应用获准访问的业务。管理端不提供停用、删除或 Token 轮换能力，已创建的数据和已发放的 Token 保持稳定。管理端应明确区分由 `token` 标识、通过 `remark` 描述的接入应用与由 `biz_type` 标识的独立业务。发号时仅允许已存在授权关系的 `(token, biz_type)` 组合通过验证。管理过程应对高风险操作提供明确反馈、记录审计信息，并避免误改会影响既有发号行为的数据。

## Affected users and systems
直接用户为平台超级管理员。受影响系统包括 `macula-cloud-admin` 管理端、`macula-cloud-tinyid` 服务及其数据库，以及用于识别超级管理员并限制管理入口和操作权限的现有认证授权链路。已经通过 TinyID 获取 ID 的接入业务也会受到业务授权关系或允许编辑的信息发生变化的间接影响。

## Constraints
管理能力仅向平台超级管理员开放，所有管理操作都需要审计。`token` 是应用接入标识，应用说明记录在 `remark` 中；`biz_type` 代表一个业务，与应用身份无关；应用访问业务的权限以 `(token, biz_type)` 组合是否存在为准。管理端不提供停用、删除或 Token 轮换能力。创建业务时，`begin_id` 和 `max_id` 初始化为 `0`，不向管理员提供设置入口。`step` 表示每次获取 ID 的步长。`delta` 和 `remainder` 配合多数据库部署使用：例如部署 5 个数据库时，各库的 `delta` 均为 `5`，`remainder` 分别取 `0` 至 `4`。`step`、`delta` 和 `remainder` 创建后默认只读，不作为常规编辑项。功能需要覆盖查询、新增、允许范围内的编辑、Token 生成和复制，以及应用与业务授权关系的维护。超级管理员可以随时查看完整 Token；Token 不得向其他用户展示，也不得写入日志或无权限响应。不得因管理能力的引入破坏现有 TinyID 发号调用。当前没有额外交付期限或兼容性要求。
