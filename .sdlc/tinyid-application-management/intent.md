# Intent: TinyID 接入应用管理
Author: Rain. Status: accepted.

## Problem
平台超级管理员目前无法通过统一管理端查看和管理接入 TinyID 的应用，也无法便捷地维护独立的业务发号配置及访问 Token，只能依赖人工操作数据库。这个过程容易产生配置错误、Token 泄露、权限失控和缺少审计记录等风险，也增加了日常接入、变更和故障处理的成本。

## Proposed outcome
平台超级管理员能够在统一管理端查询、新增和管理 TinyID 接入应用及业务发号配置，并能生成和复制访问 Token、维护应用获准访问的业务。接入应用可以删除，删除时清理该 Token 在所有数据源中的全部授权并刷新处理请求实例的 Token 缓存；其他 TinyID 实例不要求通过 Redis 等跨实例通知立即失效，可在自身缓存刷新或进程重启后收敛。发号业务仅在所有已配置数据源均存在且 `max_id` 全部为 `0` 时允许删除，删除时同步清理该 `biz_type` 的全部应用授权。管理端不提供停用或 Token 轮换能力，已经使用过的发号业务不得删除。管理端应明确区分由 `token` 标识、通过 `remark` 描述的接入应用与由 `biz_type` 标识的独立业务。发号时仅允许已存在授权关系的 `(token, biz_type)` 组合通过验证。管理过程应对高风险操作提供明确反馈、记录审计信息，并避免误改会影响既有发号行为的数据。

## Affected users and systems
直接用户为平台超级管理员。受影响系统包括 `macula-cloud-admin` 管理端、`macula-cloud-tinyid` 服务及其数据库，以及用于识别超级管理员并限制管理入口和操作权限的现有认证授权链路。已经通过 TinyID 获取 ID 的接入业务也会受到业务授权关系或允许编辑的信息发生变化的间接影响。

## Constraints
管理能力仅向平台超级管理员开放，所有管理操作都需要审计。`token` 是应用接入标识，应用说明记录在 `remark` 中；`biz_type` 代表一个业务，与应用身份无关；应用访问业务的权限以 `(token, biz_type)` 组合是否存在为准。接入应用允许整体删除，但不提供单条授权撤销、停用或 Token 轮换；发号业务仅在所有已配置数据源的 `max_id` 都为 `0` 时允许整体删除，任一数据源缺失、不可用或 `max_id` 非 `0` 都必须拒绝。创建业务时，`begin_id` 和 `max_id` 初始化为 `0`，不向管理员提供设置入口。`step` 表示每次获取 ID 的步长。`delta` 和 `remainder` 配合多数据库部署使用：例如部署 5 个数据库时，各库的 `delta` 均为 `5`，`remainder` 分别取 `0` 至 `4`。`step`、`delta` 和 `remainder` 创建后默认只读，不作为常规编辑项。功能需要覆盖查询、新增、允许范围内的编辑与删除、Token 生成和复制，以及应用与业务授权关系的维护。超级管理员可以随时查看完整 Token；Token 不得向其他用户展示，也不得写入日志或无权限响应。Token 授权缓存不新增 Redis 发布订阅等跨实例失效机制；管理变更只要求当前实例即时刷新，其他实例允许在既有缓存刷新周期或进程重启后收敛。TinyID 内新增的 Form、Query、VO 类型统一放在 `pojo.form`、`pojo.query`、`pojo.vo` 包下。不得因管理能力的引入破坏现有 TinyID 发号调用。当前没有额外交付期限或兼容性要求。
