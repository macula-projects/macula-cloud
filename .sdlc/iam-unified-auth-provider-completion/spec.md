# Spec: IAM统一认证补齐及MFA接入预留 (from intent.md 2026-11-08)
Status: accepted

## Source intent
Rain以YES接受的[intent.md](intent.md)，以及[当前源码核对报告](../../macula-cloud-iam/docs/third-party-integration.md)。既有具体来源、单协议、OIDC external_code及资源边界的接受记录继续有效；本稿仅描述增量。

## Requirements
1. 修正钉钉应用Token的appKey/appSecret、用户Token的grantType，保持企业免登与OAuth/新版SDK独立；旧SNS没有明确需求不混入。测试必须核对真实请求字段，不能只核对模拟响应。
2. 飞书浏览器、端内JSAPI及AppLink明确所用flow与版本，不失败后试另一接口。移动PKCE所需的redirect URI/verifier必须有完整受控关联；缺少材料或未核实兼容性时，不能将该flow显示为可直接使用。
3. 防重放区分“尚未提交Code”“兑换结果不确定”“已兑换后的资料失败”。后两者保留占用，重新登录取得新Code；仅能证明尚未提交Code时允许owner受控释放。保留原子claim、摘要及Client/来源绑定。
4. 应用Token按具体来源、应用/企业、凭据版本及用途隔离缓存，提前到期、并发刷新合并；停用和轮换不能继续用旧缓存。用户Token仅必要时使用，不默认持久化。
5. 企业来源支持明确的组织准入及通讯录必需、可选、后台刷新策略；平台认证与资料补充分离。非成员、账号停用、权限不足、资料缺失及依赖故障分别处理。可选资料缺失不否定已经验证的身份。
6. 现有快速开始按已关联能力选择Code Type，生成实际协议/Scope与平台逐步骤示例，区分登录Code和手机号Code。保留全部官方参考、GitHub及阿里云能力，不生成公共客户端Secret示例。
7. 预留统一MFA策略接入点，默认不要求二次认证；覆盖浏览器密码/短信/第三方、直接用户grant、绑定后网页登录及授权码/用户令牌发布边界。自定义策略拒绝或异常时不能创建完整登录态、发布授权码或令牌。
8. 账号绑定、第三方登录成功、isRequireProofKey、请求nonce或客户端传来的强度声明，均不能自动成为MFA完成证明。本轮不新增acr/amr/auth_time声明，不改变现有SSO、Refresh和资源授权策略。

## Non-goals
不重建IAM，不新增平行登录Token接口，不恢复password grant或向公共Client开放Refresh；不改变Access Token格式/aud/租户权限。不实现MFA因子、注册恢复、挑战接口或配置页面；不实现全量企业组织导入、自动创建/合并账号或覆盖本地角色权限。不提交、推送、部署或操作业务库。

## Design
### 约束与复用
遵守Cloud AGENTS.md、架构/后端/前端/测试规则、REVIEW.md及bands.yaml；本阶段使用sdlc-design。未发现额外适用的组织安全/合规技能，不虚构审查。复用现有Spring Security、Verifier、账号绑定、Redis与管理端；不引入认证框架或修改无关API Key/HMAC。

### 平台flow与关联材料
钉钉按官方SDK补证修正原Client，来源类型仍决定企业免登或新版OAuth，成员身份继续在目标应用凭据域内验证。

飞书使用受控flow标识及该flow的固定端点/字段合同；浏览器和AppLink的redirect URI必须来自来源预登记集合。现有external_code基础参数不改名；只有已核实需要第三方PKCE的flow，才允许增补经计划审查的专用关联材料，不把它混成IAM授权码的PKCE，也不接收上游URL或Secret。关联材料必须限定Client、registration、回调及有效期，不能仅凭任意verifier字符串宣称绑定完成。

是否需要最小一次性关联记录，须在实施计划中证明现有状态/票据无法安全承载后再决定；不复用账号绑定票据的用途。官方版本合同未核实前，该flow保持“待核实/不可启用”，不静默清除已有配置，不以此替代最终完成验收。

### 防重放与Token缓存
Verifier报告明确的兑换阶段和凭据消费确定性；网络超时和Code提交后的5xx默认不确定。Code成功兑换后，userinfo/通讯录失败也不得释放原占用。保留code_type+Code的跨Client防重放约束；TTL覆盖各凭据实际有效期并校验配置边界，不因调整作用域放宽跨Client复用。

应用Token缓存只在服务端，以registration、版本、固定flow及Token用途隔离；刷新加有界锁，失败不覆盖有效值、不借用其他来源。按上游expires_in计算TTL，凭据/来源版本变化后旧条目不可命中。缓存故障不允许放松认证或输出秘密。外部Code入口复用或补齐有界Client/IP限流，不能拿短信发码限流充当换码限流。

### 组织准入与通讯录
已有来源作用域和Client本地用户目录始终生效。企业成员关系用固定来源凭据验证；可返回的企业/租户标识与来源配置核对，不把请求corpId/tenant_id或个人unionId当成员证明。

新增策略区分保持既有身份路径、资料可选、成员资料必需、后台刷新。必需查询失败或无法确认准入时拒绝；可选模式仍拒绝明确的非成员/停用结果，但可容忍资料缺失或资料权限不足。只有适用来源才可选择对应能力，不让微信个人身份源伪装企业通讯录。

后台刷新仅更新已验证/已绑定成员的服务端资料和状态快照，复用既有异步/任务设施；不得自动改绑定、创建账号或覆盖本地权限。它不替代需要实时成员准入的同步校验。新策略不自动猜填历史组织；来源身份域确认后沿用不可普通替换约束。

### MFA接入点
提供可替换的服务端认证完成策略SPI，默认实现直接继续，不宣称已完成MFA。上下文只投影可信Client、租户、稳定userId、认证入口、已有认证方式、来源ID及检查阶段；不传Code、Secret、Token、session_key或客户端自报认证强度。

接入边界为：
- 浏览器首次认证：有效密码/短信/第三方认证后，在认证结果交给过滤器建立SecurityContext、Session或Remember-Me前检查；不能仅放在成功回调中，因为那时可能已保存登录态。
- 浏览器绑定完成：允许保存已证明归属的绑定，但在控制器建立完整登录态前检查；SDK绑定仍只完成绑定、不建SSO、不签Token。
- 授权发布：在授权码持久化/返回前及用户Access/ID/Refresh令牌发布前检查，覆盖SSO复用、同意授权及原生/扩展签发入口；不对服务身份伪造用户二次认证要求。

各阶段调用同一SPI，可被多次执行，要求无隐式签发副作用。SPI拒绝/异常通过安全的认证/协议错误通道失败关闭，不发布部分授权；可保留匿名授权/绑定上下文，不为拒绝某Client而清除其他合法会话。没有实际MFA处理器时不生成虚假challenge URI或复用绑定票据；本轮测试注入拒绝策略验证接入点，默认不增加用户操作或改变响应。

SSO复用和Refresh仅预留检查阶段，默认语义不变；未来MFA模块必须明确会话复用、认证时效、刷新及证明持久化，不能以本次SPI存在宣称这些策略已经实施。

## Data and interfaces
- 复用OAuth Client、SourceType、CodeType、registration及账号绑定模型；补充明确flow、组织准入/通讯录策略及适用的回调约束，服务端和管理端使用同一能力目录。
- 基础external_code参数与none认证保持；新增关联材料必须按flow精确允许、拒绝重复/未知/跨来源参数，并记录协议变更。具体字段及范围在计划中固定，不能实施时随意放宽白名单。
- 应用Token/成员快照仅服务端保存，按数据敏感性隔离及加密；不进入日志或前端持久状态。缓存键使用摘要，避免直接暴露敏感主体。
- 必要数据库变更使用当前最高版本之后的追加迁移；不改V14—V19，不猜填组织/绑定/权限。没有MFA因子表或MFA开关。
- 管理端呈现真实可用能力、未核实原因、策略说明与所选能力示例；现有文档保留链接，明确模拟验证和真实平台验收的差别。

## Flagged concerns
- 飞书官方合同未完整读取：AppLink/端内Code与Token版本兼容性及必要PKCE关联必须取得官方证据；未核实flow不得启用或宣称完成，blocking（对应flow的启用/验收；责任：实施者）。
- 参数白名单与新关联材料：现有合同不携带第三方PKCE材料，若需新增必须在计划中明确最小合同和威胁边界，不能仅忽略verifier；需要Rain接受该有条件扩展，blocking。
- 重试可用性变化：Code提交后超时需重新取Code，不能承诺原Code重试成功；替代旧的统一网络/5xx释放约定，需要Rain接受，blocking。
- MFA挂接遗漏：成功处理器太晚，绑定控制器、SSO/同意授权及原生签发可能绕过单点检查；必须有拒绝策略的真实安全链证明，未证明前不能称接入点完整，blocking（实现验收）。
- 默认行为与后台刷新：默认保留既有认证路径；后台刷新不做全量导入、不覆盖本地账号权限，不替代实时准入。需Rain接受此边界，blocking。
- 真实平台与权限条件：Mock和本地Redis/MySQL不能证明设备SDK、应用权限或厂商往返；提供能力矩阵和未验收清单，non-blocking（本地构建），真实支持声明仍需对应证据。

## Verification strategy
1. 平台HTTP合同：精确断言URL、方法、字段名、Token类型及来源隔离；覆盖Code无效、非成员、缺字段、无资料权限、3xx、超时及5xx，检查日志无敏感材料。
2. 原子与缓存：并发同Code最多一次进入兑换；提交前可控释放、提交不确定/已兑换保持占用；TTL边界、跨Client/来源、Token单次刷新、停用/轮换及依赖故障分别验证。
3. 准入与绑定：真实Mapper/事务和专用MySQL/Redis验证现有绑定、自动/手动绑定、成员与资料策略、后台状态更新及来源变更；不碰业务库。
4. MFA：默认SPI回归密码/短信/第三方/授权码/OIDC external_code；注入拒绝及异常SPI，证明无完整新Session、无可用code、无Token/半份授权。覆盖绑定后网页登录、已有SSO及同意授权、Refresh；SDK绑定不建会话，client_credentials不被当作用户认证。
5. OIDC/OAuth与资源：验签ID Token及可选nonce、openid/Scope、UserInfo、JWT/opaque aud一致，Gateway/System既有允许和拒绝边界不变。
6. 最小Maven后扩大Cloud相关回归；Admin Vitest、无修复ESLint、构建与Cypress桌面/移动验证目录、flow/策略、能力选择和真实示例。分别报告静态、单元、Mock、隔离集成与真实平台证据。

## Acceptance
Rain以YES明确接受本设计及全部flagged concerns，包括有条件关联材料扩展、Code结果不确定时重新取Code、MFA覆盖证明和后台刷新边界。飞书官方合同核实及真实安全链证明仍是对应能力启用/验收前提，不因批准而视作已有证据。不包含源码实施、提交、推送或部署批准。
