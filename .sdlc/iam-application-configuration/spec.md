# Spec: IAM 应用配置模型与接入体验重构 (from intent.md 2026-11-06)
Status: accepted

## Source intent
[intent.md](intent.md)：Rain 已确认按应用架构、应用配置、协议配置、登录控制和独立身份源重构，并允许参考 Authing 官方文档。参考核对见 [research.md](research.md)。

## Requirements
1. 创建时只选择应用类型、填写名称和认证租户/必要用户范围；可按模板要求补充回调或身份源。Client ID 自动生成并只读，复用当前安全随机生成与服务端唯一性/不可变校验，不要求手写协议值。
2. 应用类型为标准 Web（WEB_SERVER）、单页 Web（SPA）、本地客户端（NATIVE）、后端服务（SERVICE）、小程序（MINIAPP）。微信/企微只作为小程序平台或身份源渠道，不与这些架构类型平铺；端内网页归属 Web/SPA 的登录渠道。
3. 新建阶段切换类型或小程序平台，清空原类型登录能力、身份源绑定、直登、回调及派生授权，重新应用新模板；名称和用户已填的通用参数保留。创建后类型/小程序平台只读；历史未分类记录允许显式确认一次。
4. 创建成功进入详情，使用四个分区：应用配置、协议配置、登录控制、接入指南。各分区保存前端已编辑内容时必须保留其他分区值，并在失败/切换时处理未保存状态；复用既有 REST 资源，不改成独立的新业务应用实体。
5. 应用配置展示名称、类型、Client ID、密钥状态、回调和精确 Origin；密钥仅新建/重置时提供原文与复制，关闭后清除。公有客户端不展示无用途的密钥输入。读取已保存配置不能恢复密钥。
6. 展示可复制的 Issuer、Discovery、授权、Token、UserInfo、JWKS、内省、撤销和退出端点，以实际 Discovery 支持字段为准。平台端点只读；地址获取失败显示明确状态，不根据管理端 Origin 或示例域名伪造地址。平台不新增每个应用独立认证域名。
7. 协议配置仅呈现已实现的 OAuth2/OIDC。新 Web/SPA/本地客户端模板默认授权码，公共客户端强制 S256 PKCE；后端服务默认 client_credentials，禁止 none、用户登录和无意义的刷新令牌。小程序默认 external_code 和明确的凭证类型/身份源；也允许单独启用 IAM 统一登录（authorization_code + S256 PKCE），或两条入口并存。刷新开关表示允许使用已签发刷新令牌，不承诺所有 grant 都签发它。
8. 客户端认证使用中文名称和协议值；Web 默认 client_secret_basic，可使用现有密钥表单或 private_key_jwt。SPA/本地客户端/小程序默认 none。类型用于提供正确模板，服务端仍校验实际凭据与授权组合；特殊的已存在组合明确显示为兼容配置，不静默禁用或转换。private_key_jwt 保持填写客户端 HTTPS JWKS URL 和算法，与只读的平台 JWKS 分开。
9. 授权模式使用紧凑复选框。password、sms、email 和 external_code 的底层参数放在有明确用途的扩展/兼容区域，不能用托管页短信开关隐式开启 sms grant。新模板不提供 implicit 或默认开启 password；保留旧兼容数据和现有拒绝边界。本轮只有统一客户端认证设置，不增加没有后端实现的内省/撤销独立认证选项。
10. 登录控制分成托管登录页与外部登录渠道。托管页先支持当前真实存在的密码、手机验证码，新增 Client 级 PASSWORD/SMS 策略；页面展示、POST 登录和验证码发送都读取同一受控 Client 策略。不能通过隐藏按钮代替服务端拒绝。全局关闭优先于 Client 开关；没有 Client 上下文的既有门户行为保持兼容，不由任意 client_id 参数取得受信任身份。
11. 策略作用域必须清楚：托管页方式开关控制新发起的托管页认证，不等同于 Token 扩展 grant 开关，也不追溯撤销已有 SSO 会话。已有 SSO、Token 和访问权限不由这些 UI 开关重新定义；不新增 MFA/step-up。当前托管页未实现的邮箱验证码、注册等不展示为可用开关。
12. 身份源凭据在现有身份源管理中配置；应用只关联已有的已启用兼容渠道，显示名称及能力。网页登录保持同平台全局唯一启用源的实际限制；零个/多个时说明原因并拒绝新关联。SDK/小程序沿用 Client 固定 registration 绑定。取消关联只影响本 Client，不删除或禁用平台身份源。
13. 接入指南按类型提供必要步骤、可复制地址和请求示例，真实 Secret 默认遮蔽；private_key_jwt 签名脚本仅在客户端执行，不上传私钥。没有真实受控体验登录闭环前不提供会误导的“体验登录”按钮。
14. 旧 Client 的 ID、密钥、grant、身份源与用户绑定不回填或重置；类型不靠凭据/渠道推断。未分类记录显示待确认，可继续维护原有非类型配置；明确确认类型时展示差异，发现不兼容项由用户处理后保存。类型已确定后，新 UI 和服务端遵循同一不可变约束。
15. 桌面使用详情布局而非把全部配置塞进长抽屉；窄屏分区可切换，只有代码容器可横向滚动。说明按需查看，只对实际冲突报错；异步目录、Discovery、保存和复制失败均提供可操作状态。

## Non-goals
不照搬 Authing 的注册、MFA、生物识别、CAS/SAML、独立应用域名、完整访问授权或账号自动合并；不合并 sys_application/API Key 与 IAM Client；不托管私钥或提供密钥哈希反解；不修改真实 Client、业务数据、推送或部署。浏览器多 registration 的身份域改造不属于本轮。

## Design
System 管理配置和持久化，IAM 执行认证策略，Admin 提供创建与详情体验；Gateway 仅核对路由和权限。沿用 Vue 3/Element Plus、现有路由/菜单与 API 封装。四分区复用一份脱敏配置草稿，保存完整时保留未修改字段；敏感临时值不进入持久状态和普通更新请求。

创建：选择架构类型→系统生成 ID/适用密钥与模板→填写该类型必需项→保存并进入详情。标准 Web 与 SPA 的区别在于实际凭据保管/换 Token 位置；小程序平台仅在 MINIAPP 时选择。登录渠道选择发生在登录控制，不再通过反复切换“终端导航”模拟勾选归属。

协议字段保留既有机器标识；应用类型是配置模板和校验维度，不把 OAuth Client、终端供应商和外部身份源当成同一概念。手机号/邮箱作为密码登录标识的能力与用户目录实现一致，不以界面枚举承诺尚未安装的用户来源。

IAM 的 Client 级托管策略复用受控授权请求上下文，并核对注册 Client、grant、回调关联等。密码/SMS 提交及浏览器验证码发送共用校验；短信验证码绑定相同 Client 上下文，拒绝跨 Client 使用。默认继承旧全局策略用于历史记录；明确写入后按 Client 配置限制。Token 扩展接口仍保留现有 Client/Origin/grant 校验，不借本次重构扩大允许范围。

元数据通过 System 的只读管理接口读取受信任 IAM Discovery。获取地址由服务端配置、超时和缓存控制，不接受请求中任意 URL；必要时区分内网获取地址与对外 Issuer。页面展示 Discovery 发布的外部地址，缺失字段不自行补全成“可用端点”。

## Data and interfaces
沿用 `/api/v1/oauth2-clients` 和既有字段，增加 `applicationType`、MINIAPP 条件下的 `miniappPlatform`、`hostedLoginMethods`。对应数据库字段可空：`application_type`、`miniapp_platform`、`hosted_login_methods`；null 登录策略表示历史继承，不等于空集合（明确关闭）。同步 System Form/VO/Entity、IAM 只读映射和共享策略标识；新建要求明确类型，旧 PUT 省略新字段必须保留原值。

新增只读 Discovery 管理接口及其配置来源说明；不返回任何凭据。创建/重置继续使用原有接口和单向密钥保存，原文仅在当前操作内存中暂存。没有新增三套端点认证字段、浏览器多源绑定表或权限表。

上一轮未部署的 V14 terminal_type 及相关实现不作为上线前提。计划阶段逐项列出可复用的 UUID、复选框、编码、密钥生命周期与测试，以及需要替代的终端模型；核实 V14 在所有目标环境未执行后再整合迁移，已执行环境必须新增迁移。历史 SDLC 记录保留，不重写其证据。

## Verification strategy

## 2026-11-10 按登录入口分离的确认补充
Rain明确说明小程序/移动客户端均可直接提交平台Code，也可打开IAM统一登录页，并在完整模型展示后回复“是的”。本补充替代之前按MINIAPP架构排除统一登录/网页来源的限制。

- IAM统一登录与平台Code是两条独立入口。同一公共Client允许authorization_code与external_code并存；小程序可仅统一登录、仅本平台Code或两者并存。SERVICE继续禁止用户登录。公共授权码使用S256 PKCE，沿用已登记回调、state及OIDC nonce约束。
- 网页身份源按实际浏览器/容器能力显示；允许应用关联来源不表示每个容器都能使用。不能把“手机浏览器支持”推导为“小程序内嵌web-view一定支持”。平台Code继续按已保存架构、平台、具体registration校验，拒绝客户端自报终端绕过。
- 小程序主动打开IAM登录页默认保留密码/短信和适用网页入口，不因微信UA直接跳走；明确配置直登时才自动续转。Web/SPA的企微端内自动网页授权、飞书/钉钉JSAPI Code路径保持。
- 新小程序的hostedLoginMethods为null继承平台策略；已有显式[]仍表示关闭，不重置已有配置或身份绑定。启停统一登录不删除已有Code关联；有关联的网页来源时须先移除关联才可关闭。
- 小程序业务方负责web-view业务域名、回调页面与授权码返回桥接；IAM不把Access Token放入回跳URL。本轮未实现业务小程序SDK或桥接，也未完成真机/真实第三方联调。

验证补充：覆盖小程序三种入口组合、开关保留Code与显式空策略、错误平台拒绝，以及微信UA打开IAM页后密码登录→授权码→PKCE换Token。沿用原Proof中隔离数据库迁移和并发证据；本轮无Schema变化，不重复宣称执行迁移。


## 2026-11-10 身份源多能力模型修订（Rain已批准实施）

需求来源：Rain在凭据逐接口核对清单展示后要求“好，改一版”，并进一步明确“微信的应用要分开的，他的管理端都是独立创建不同类型应用的”。此处完整记录该要求；新增数据/接口方案及独立计划复审完成后，Rain回复“OK”批准本轮实施；不以原规格accepted状态替代本轮批准。

1. 一条身份源对应一个真实第三方应用注册及其凭据。微信网站、移动应用、公众号/服务号、小程序独立建源，分别保存AppID/Secret；不建立微信开放平台聚合源或分组表。企微同一自建应用共享CorpID/AgentID/Secret；企微小程序能力使用所关联企微应用的配置。飞书同一App ID/Secret支持多能力。钉钉只允许已核实的新合同，旧SNS及未核实SDK不能因多选而放开。
2. 应用注册类型与登录能力分离：前者单选并在创建后固定，后者按该注册的真实支持范围多选。多能力只引用同一真实注册凭据；不能用共同企业ID或UnionID合并不同注册。
3. 企微能力分别为PC网页、端内网页、已核实移动SDK、关联小程序；飞书为网页OAuth、AppLink、端内JSAPI Code；微信各注册只显示相应能力，小程序可分别启用登录Code/手机号Code。GitHub、阿里云和现有仅配置型来源保留既有能力，不因本轮退化。
4. 页面不显示flow、版本、通讯录策略。每项能力只显示确有必要的回调、Scheme或关联说明；无相关实现时不新增伪造校验参数。已存在显式历史flow不静默升级，新能力采用核实后的固定默认合同。
5. 应用登录控制关联“能力→具体registrationId”，按已保存应用类型、入口及实际环境检查。微信同平台不同网页能力可分别固定网站/服务号来源。不得只在前端过滤；页面、显式发起、自动直登、回调、external_code及账号证明都再次核验能力和固定来源。
6. 旧registrationId、密文、Client ID及现有用户身份绑定不改写；已有记录只补登记其原来实际具备的能力，不自动启用额外能力、不按凭据相同自动合并记录。网页登录已有注册级身份绑定服务继续复用，不建平行绑定体系。
7. 新能力或凭据变化递增来源版本；停用能力立即使新发起/在途回调/待绑定票据拒绝，不绕过目录准入或防重放。关闭能力可保留失效应用引用供修复，不静默删除引用/用户绑定。
8. 首版不自动按UnionID合并不同微信注册的账号绑定；首次新增注册沿用现有账号证明/可信映射。企微手机号邮箱敏感授权仍保持用户选择的暂缓范围。

验证补充：隔离MySQL V21→新版本、旧源/密钥/绑定快照、旧请求省略字段保留能力、并发修改CAS、能力跨平台拒绝、网页能力固定来源及注册隔离、两种小程序Code固定接口、停用/改密后的在途拒绝、账号证明及Code防重放回归；Admin多选保存/回显/增减能力/微信四类型独立凭据及1440/390px布局。

本修订替代原Non-goals中浏览器多registration的排除项，仅允许不同明确能力固定不同注册，不开放请求参数任意选择注册，也不迁移/合并用户身份域。
