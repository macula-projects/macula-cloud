# Intent: IAM 应用配置模型与接入体验重构
Author: Rain. Status: accepted.

## Problem
IAM Client 页面把应用类型、用户登录方式、客户端认证、OAuth grant 和第三方身份源混合展示。管理员难以知道先配置什么、哪些内容由系统提供，也容易把登录页验证码与直接验证码授权、平台 JWKS 与客户端 JWKS 混淆。仅缩小卡片和增加说明无法解决模型和配置流程的问题。

## Proposed outcome
以真实应用接入架构创建应用，再在应用配置、协议配置、登录控制和接入指南中分别维护相应内容。应用 ID 自动生成；平台端点清晰可复制；身份源独立配置后由应用关联。用户能根据实际能力完成常见接入，无需先理解内部字段组合。

## Affected users and systems
应用接入人员、平台管理员；Macula Cloud Admin、System、IAM 及共享配置契约。Gateway 用于核对入口和权限边界，不将 IAM Client 与已有业务应用/API Key 管理实体合并。

## Constraints
参考用户提供的 Authing 截图和官方文档，协议行为仍以现代规范及 Macula 实现为依据。保留当前未提交成果，明确整理可复用部分及被替代的终端模型。既有 Client ID、密钥、授权和身份绑定不自动改写。private_key_jwt 保持客户端 JWKS URL；不托管客户端私钥。只呈现后端真实支持并可验证的能力。

## Open questions
应用类型编辑限制、历史配置收敛和新增登录策略的具体行为由 spec 明确提出并审阅；不将此前“编辑状态不能再改”的歧义默认为用户已选定某一策略。

接受依据：用户提供七张 Authing 截图，要求重新审视配置模型；在助手提出按应用类型、应用配置、协议配置、登录控制和独立身份源组织后，用户明确回复“确认，你也可以去参考authing的网站文档”。本文件记录该范围确认，不代表接受后续尚未审阅的 spec/plan。
