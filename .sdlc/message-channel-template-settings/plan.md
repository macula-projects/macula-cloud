## Order of work
1. Lock the schema and catalogs: add the V5 preflight/constraint migration without modifying V1–V4, define the exact four mail providers, two SMS providers, eight mail scenes, nine SMS scenes, `zh-CN`/`en-US` languages, provider presets, and fixed variable allowlists. The migration fails on multiple provider rows per channel instead of silently choosing or deleting data.
2. Refactor System provider management from list CRUD to one global configuration per channel. Replace free-form `configJson`, arbitrary endpoint/provider values, IDs, delete, Exchange, and custom SMS with typed provider fields and server-side SMTP presets. Preserve the approved rule that a blank secret on update keeps the encrypted value, while a new configuration requires it.
3. Refactor template management and test delivery. Return the complete fixed scene set, support mail custom/default state and SMS provider/language template codes, render only declared variables, sanitize mail HTML with a server-side allowlist, expose sandbox-safe preview content, and send tests only through the enabled current provider with cleaned errors, throttling, and non-sensitive audit fields.
4. Keep credential encryption delegated to Macula Boot. Per the engineer's 2026-10-17 scope decision, Macula Cloud does not change or verify `@CryptoField` encryption-exception behavior in this change; retain no-echo and blank-update semantics at the Cloud API boundary, and continue implementation without an upstream encryption gate.
5. Implement IAM login SMS against the shared `macula-system` schema, as explicitly chosen. IAM gets local read-only table mappings rather than importing System Java classes, enables the same `@CryptoField` configuration, reads only the enabled SMS provider and `SMS_LOGIN` template, and dispatches via the existing Aliyun/Tencent SDKs. Missing, disabled, ambiguous, invalid, or undecryptable configuration fails closed.
6. Replace the permissive IAM verifier with a real one-time-code lifecycle: cryptographically random code, irreversible digest, Redis TTL, phone-hash and IP throttles, bounded failures, atomic one-time consumption, and record creation only after supplier acceptance. Add a CSRF-protected same-origin send-code endpoint with normalized phone input and a generic response, then wire the existing login page button/countdown without adding registration, recovery, binding, welcome, or expiry workflows.
7. Rebuild the Admin message settings page to the three accepted tabs. Mail templates show the eight scenes with configure/browse actions and a sandboxed preview; mail service shows a single enable/provider form; SMS service shows a single enable/provider form plus the nine scene template-code rows, language switch, and per-row test. Add loading, empty/error, validation, save locks, secret placeholders, and Chinese/English locale text; remove Exchange, custom SMS, Qiniu, free-form endpoints, multi-provider list/add/delete, and the fourth tab.
8. Update module documentation and tests, then record any file or ordering deviation in this plan before asking whether implementation is complete.

## Risks
- IAM direct access to System tables is an approved exception to the repository's default cross-service API boundary. Local IAM mappings prevent Java implementation coupling, but schema rollout and rollback must keep IAM and System versions coordinated and both services must point to the same database/schema.
- IAM must receive the same `MACULA_CRYPTO_PASSWORD` as System to decrypt SMS credentials. A missing or mismatched key must disable login-code delivery rather than leak, overwrite, or log secrets.
- Macula Boot currently documents a possible fail-open encryption interceptor. The engineer explicitly moved correction and verification of encryption-field exception behavior to a future Macula Boot change; this Cloud change neither works around nor verifies that framework behavior.
- V5 cannot infer which legacy provider row should win. Because compatibility/migration was declined, it will stop on multiple rows and require an explicit operator cleanup before applying the unique-per-channel constraint; it will not silently delete data.
- Supplier SDK acceptance is not final delivery. Automated tests use fakes; real Aliyun/Tencent acceptance needs isolated credentials, approved bilingual templates, network access, and non-personal test numbers.
- Redis atomicity is security-sensitive. TTL, attempt counter, send throttles, and one-time consumption must be expressed as atomic operations/Lua and tested for replay and concurrency.
- Mail HTML requires both server sanitization and iframe sandboxing. Either layer alone is insufficient; allowed tags/attributes must remain deliberately small and links/images must not enable scripts, forms, or parent navigation.
- The current message-settings code belongs to an earlier broad feature and includes out-of-scope providers and CRUD. Removing those behaviors is intentional, but tests and docs that still assert them must be updated together.
